# Единый retry через redelivery RabbitMQ вместо отдельного in-process retry для webhook

ТЗ требует retry как при сбое обработки сообщения, так и при сбое отправки webhook (3 попытки, экспоненциальный backoff), и DLQ после исчерпания попыток. Вместо отдельного in-process retry-лупа для webhook, Consumer при неудачной отправке делает `nack`, и повторная попытка — включая backoff и итоговый уход в DLQ — выполняется механизмом redelivery самого RabbitMQ, единым и для сбоя обработки, и для сбоя доставки webhook.

Это исключает дублирование retry-логики и не блокирует async-воркер сном в цикле. Плата за это: Consumer обязан быть идемпотентным относительно уже терминального статуса платежа — при redelivery он не переигрывает Gateway emulation (90/10 исход), а повторяет только отправку webhook.
